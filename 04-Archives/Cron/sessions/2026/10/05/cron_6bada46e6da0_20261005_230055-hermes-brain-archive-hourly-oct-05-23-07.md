When this fires (or fires repeatedly while iterating on a file full of regexes), stop trying to out-guess the escaping with `patch` — read the full current file with `read_file` (every page if paginated) and rewrite it whole with `write_file` instead, which takes the literal string content with no re-escaping step.\n- **`write_file` refuses to overwrite a file that was last read via `read_file` with `offset`/`limit` (a partial page), even if you believe you have the full content from an earlier full read in the same conversation** — it errors \"was last read with offset/limit pagination\" and does not write. Call `read_file` again with no offset/limit (or page through every remaining chunk) immediately before the `write_file` call that will replace that file, not just once earlier in the session.\n\nSee `references/cron-and-hook-isolation.md` for: separating cron plumbing from Daily/ session content, why post_llm_call hooks crash Obsidian, and local-path-leak grep false positives.\n\n## Pitfalls\n\n- **A \"there's an update available\" banner in the vault's Dashboard (which compares its own `VERSION` file against GitHub's latest *release tag*) can be a false positive: the maintainer tagged a release without bumping `VERSION` in that same commit.** Before assuming a pull will fix it, diagnose first: `git fetch origin --tags`, then compare `git log --oneline origin/main -1` against `git rev-list -n 1 v<the-flagged-version>` — if they're the SAME commit SHA, and `git merge-base --is-ancestor origin/main HEAD` says yes, the vault already has everything that commit contains; there is nothing to merge. Confirm by reading `VERSION` inside that commit (`git show <sha>:VERSION`) — if it still shows the OLD version number, the tag/VERSION drift is the maintainer's bug (see the release procedure's VERSION+CHANGELOG-same-commit rule above), not something a pull on the consumer side can fix. Report this plainly instead of re-running fetch/merge in a loop hoping for a different result.\n\n- **When adding a new vault automation script that integrates with `hourly_archive.py`, import `subprocess` at the top of the module — never do a local `import subprocess` inside a try/except block.** Python treats any variable assigned in a function (including imports) as local to that function for the entire scope, so a local import after an earlier `subprocess.run()` call causes `UnboundLocalError: cannot access local variable 'subprocess' where it is not associated with a value`. Normalize paths with `path.replace(chr(92), \"/\")` (chr(92) = backslash) rather than `path.replace(\"\\\\\", \"/\")` which doesn't match the actual single-backslash characters in the stored string. Also normalize the VAULT root if it comes from git-bash (`/c/Users/...`) by converting to `C:\\Users\\...` before `os.path.join()` — use `os.path.normpath()` after the drive-letter conversion.\n\n- **A `session_tagger.py`-style script must handle the case where the manifest doesn't exist yet, is empty, or has entries whose session files have already been deleted.** Wrap the file existence check after path normalization, skip missing files silently, and only rewrite the manifest if at least one new tag was added. Before touching structure: (1) clarify what \"organize\" means — hygiene (gitignore stray generated files, commit orphaned untracked scripts, tidy `.gitignore`) is safe and should just be done; genuine folder/file reorganization is not, (2) if the user does want a real reorg, tell them explicitly it creates permanent merge debt against the template and get their go-ahead before executing, rather than assuming silence means proceed.\n- **If `User-Profile.md` (or any file the `merge=ours` fix targets) keeps hard-conflicting on repeat updates, the fix documented below was never actually wired into this vault's `update.sh`/`update.ps1` — don't just re-document the technique again, check `git check-attr merge \"User-Profile.md\"` in the vault; if it doesn't report `merge: ours`, that's the real gap to close (add the `git config merge.ours.driver true` + `.git/info/attributes` lines to the update script itself so every vault self-heals on next run, not just this one).**\n- **A template-shipped scaffold file the user is expected to fill in locally (e.g. `User-Profile.md`) will hard-conflict on every future template update once the user edits it, because the template keeps shipping its own version of the same filename.** `.gitignore` cannot fix this — an ignored path can never be *added* by a future merge either, so a brand-new vault would never receive the scaffold at all. The correct fix is a **local-only `merge=ours` git attribute**, set up by the install/update script itself on every run: `git config merge.ours.driver true` plus appending `<file> merge=ours` to `.git/info/attributes` (never `.gitattributes` — that file is tracked and would ship the rule into the template repo itself, which is wrong; this is vault-local config only). Effect: the first pull still delivers the blank scaffold normally (file doesn't exist locally yet, so it's a clean add, not a conflict); every pull after that resolves any conflict by silently keeping the local copy, no matter how the template's own version changes. Do NOT apply this to files the user is expected to keep merging with the template's real improvements (e.g. `.obsidian/appearance.json`, a bundled theme's `theme.css`) — for those, a real conflict is doing its job, and `merge=ours` would silently discard legitimate template updates; document the manual `git checkout --ours/--theirs` resolution for that class instead. A file write succeeding is not evidence the block is syntactically valid.
